# S2.06 / S2.07 · Séries de métriques, énergie et pas

**Fiches source** :
`Downloads/LKDV_Lancement_Autonome 2/fiches/Strava/S2.06.md` et
`S2.07.md` (hors dépôt, lues pour cette passe). Elles demandent
respectivement :

- S2.06 — importer les séries cardio, cadence et température, puis afficher
  moyennes, pics et qualité de mesure ;
- S2.07 — afficher les estimations d’énergie et les pas **quand la source les
  fournit**.

## Décision de périmètre

La seule source réellement branchée dans l’Explorer v2 est le GPS du
navigateur (`navigator.geolocation`). Le tracker accepte les points et expose
l’altitude et, quand le navigateur la rapporte, la vitesse. Aucun connecteur
cardio, cadence, puissance, température, podomètre ou énergie n’existe dans
le dépôt à cette révision.

La livraison ne fabrique donc aucune de ces mesures :

| Métrique | Source actuelle | Affichage |
|---|---|---|
| Altitude | `GpsFix.ele` d’un point accepté | série mesurée GPS |
| Vitesse | `GpsFix.speed`, sinon distance/temps du tracker | série mesurée ou calculée |
| Allure | dérivée d’une vitesse strictement positive | série calculée |
| Fréquence cardiaque | aucune | absence explicite, aucune valeur |
| Cadence / pagaie | aucune | absence explicite, aucune valeur |
| Puissance | aucune | absence explicite, aucune valeur |
| Température | aucune | absence explicite, aucune valeur |
| Calories | aucune | absence explicite, jamais déduite |
| Pas | aucun podomètre | absence explicite, jamais déduits |

Lorsqu’un connecteur les fournira, l’énergie et les pas sont traités comme des
**totaux cumulés depuis le départ** : la vue affiche la dernière valeur
fournie, pas une moyenne de compteur. Les autres métriques affichent une
moyenne, un pic et un nombre de mesures.

Les cartes `metricSeries` d’une séance ne contiennent que des valeurs reçues.
Une lacune ne crée aucun point, n’est jamais interpolée et ne devient jamais
un zéro. Les calories et les pas ne sont jamais calculés à partir de la
distance, de la durée ou du poids.

## Contrat livré

### Types (`state/types.ts`)

- `MetricKey` : `elevation`, `speed`, `pace`, `heartRate`, `cadence`,
  `strokeRate`, `power`, `temperature`, `calories`, `steps`.
- `MetricSource` : `gps`, `sensor`, `import`, `derived`, `mixed`.
- `MetricQuality` : `measured`, `derived`, `estimated`.
- `MetricSample`, `MetricSeriesStats`, `MetricSeries`.
- `ActivityState.metricSeries?: MetricSeries[]` : absent sur les scènes et
  les bilans antérieurs, ce qui laisse l’interface vide au lieu d’inventer
  des valeurs.
- `ActivityState.clientSessionId?: string | null` et 4ᵉ argument optionnel de
  `startActivity` : identité locale A01, sans laquelle aucune reprise n’est
  possible. Les appels historiques restent valides.

Les valeurs sont canoniques : m, m/s, s/km, bpm, spm, c/min, W, °C, kcal,
pas. La conversion d’affichage (km/h, mph, ft, °F, allure) est faite au
rendu.

### Moteur pur (`activity/metrics.ts`)

- `appendMetricInputs` / `buildMetricSeries` : ajoutent uniquement les champs
  finis fournis par une source. `null` est ignoré.
- `summarizeMetricSeries` : moyenne, minimum, maximum, première/dernière
  valeur et durée, calculés sur **toutes** les valeurs reçues, y compris
  celles qui ne sont pas conservées dans l’échantillonnage d’affichage. La
  moyenne est pondérée par le temps entre mesures (intégration trapézoïdale),
  plafonnée à 60 s ; au-delà d’un trou, la moyenne simple des valeurs reçues
  prend le relais, sans pont inventé.
- `formatMetricValue`, `metricQualityLabel` : formats honnêtes, avec `—` pour
  une valeur non finie.
- `unavailableMetricsForSport`, `METRIC_UNAVAILABLE_REASONS`,
  `groupUnavailableMetrics` : expliquent une absence par sport, sans produire
  de valeur.

L’échantillonnage d’affichage garde un point toutes les 5 s ; les agrégats
restent exacts. L’allure est dérivée de la vitesse ; la vitesse d’intervalle
n’est dérivée que lorsque le GPS ne la fournit pas, et seulement depuis une
distance réellement ajoutée par le tracker.

### Branchement GPS (`activity/useGpsTracker.ts`)

À chaque point **accepté** par `ActivityTracker` :

1. l’altitude brute du point alimente `elevation` (qualité `measured`, source
   `gps`) ;
2. la vitesse rapportée par le navigateur alimente `speed` (qualité
   `measured`, source `gps`) ;
3. si le navigateur ne rapporte pas de vitesse, la vitesse d’intervalle est
   dérivée de la distance réellement ajoutée par le tracker et du temps
   corrigé (`source: 'derived'`, `quality: 'derived'`) ;
4. une nouvelle borne (`metrics.discontinuity`), une pause ou un trou GPS
   interdit la vitesse dérivée : aucune corde droite n’est inventée ;
5. l’allure est recalculée depuis la vitesse.

Le dernier point accepté est borné à la séance (`sessionId` + `startedAt`) :
un nouveau départ ne peut pas hériter du point précédent.

### Affichage

- `sheet/MetricSeries.tsx` : panneau partagé. Il affiche les séries qui
  contiennent au moins une valeur, avec moyenne, pic (ou « meilleure » allure),
  nombre de mesures, qualité et sparkline construite sur les échantillons
  réels.
- Onglet `Mesures` de la séance en direct (`sheet/SheetContent.tsx`) :
  remplace l’ancien onglet `Cœur` qui affichait une absence statique. Les
  séries GPS disponibles sont visibles, et les capteurs pertinents non
  branchés sont regroupés en « Non disponible ».
- Onglet `Statistiques` du `Bilan` : reprend le même panneau depuis
  `summary.metricSeries`. Le bilan vide affiche « Aucune série mesurée », pas
  des zéros.

Aucun nouvel écran, aucun filtre standard par défaut, aucune interface
Compte n’a été modifiée.

## Conservation et restauration

### Ce que la révision 8321e66 permet réellement

À cette révision, `ActivityState` vit uniquement dans le store Zustand : il
n’existe ni `clientSessionId`, ni magasin IndexedDB de séance, ni rejeu des
points au montage. Un rechargement de page perd donc l’activité, ses points et
ses séries. Le seul contrat serveur branché est la **fin de sortie**
(`/api/explorer/v2/activity/finish` → `finish_activity_session_idempotent`),
qui agrège distance, D+ et durée ; le client courant ne crée pas de séance et
n’alimente pas `activity_points`.

Il n’y a donc **aucune conservation réelle possible** à 8321e66 sans
réimplémenter la persistance A01. Cette passe ne la réimplémente pas en
parallèle et ne prétend pas que les séries survivent à un rechargement.

### Ce que la branche intégrée 4e0a25c apporte

A01/A02 y ajoutent une fiche de séance locale (`LocalSessionRecord`, version 1,
magasin `sessions`), chaque point GPS **réellement accepté** avec `t`, `lat`,
`lng`, `ele`, `acc`, `speed`, et une reprise au montage :

- `readActiveSession()` + `readSessionPoints()` fournissent les points déjà
  acceptés ;
- `ExplorerV2` les passe à `useGpsTracker({ restored })` ;
- `readLatestFinishedSession()` + `readSessionPoints()` + `activityFromRecord()`
  restituent le dernier bilan et ses points.

Cette base conserve donc déjà **tout ce dont les séries GPS ont besoin**.
Aucune donnée de santé n’y est ajoutée.

### Raccordement retenu : reconstruire, pas dupliquer

Les séries GPS sont une **projection déterministe** des points conservés. Elles
ne sont pas un second stockage :

- `rebuildMetricSeriesFromFixes(fixes, sport, autoPauseEnabled)` rejoue les
  points acceptés avec le même `ActivityTracker` et les mêmes règles que le
  direct : altitude mesurée, vitesse rapportée, sinon vitesse d’intervalle
  dérivée uniquement quand le tracker a réellement ajouté de la distance et que
  la continuité est prouvée ; allure dérivée de la vitesse ;
- `rebuildMetricSeriesFromPoints(points, sport, autoPauseEnabled)` applique la
  même reconstruction à `LocalSessionPoint[]` (bilan restauré), sans dépendre
  du magasin local ;
- `useGpsTracker` restaure d’abord le tracker avec le profil de pause du sport
  **avant** le rejeu, republie distance, D+, durée en mouvement, splits et
  tours, puis republie `metricSeries` ;
- `previousMetricFixRef` repart du dernier point rejoué : le premier fix vivant
  ne compte pas deux fois le segment déjà persisté ;
- `mergeMetricSeries` remplace uniquement `elevation`, `speed` et `pace` et
  conserve les autres séries si une source réelle en fournit un jour.

Ce raccordement n’ajoute **aucun magasin IndexedDB**, ne change pas
`EXPLORER_DB_VERSION`, n’ajoute aucun champ `metricSeries` à
`LocalSessionRecord` pour les séries GPS, n’écrit aucune migration Supabase et
ne crée aucune valeur cardio, énergie ou pas. Il reste inactif sur 8321e66 tant que la
persistance A01 n’est pas fusionnée : c’est le contrat de reprise qui manque,
pas la reconstruction.

### Raccordements exacts à faire sur 4e0a25c

1. **`state/types.ts`** : conserver `clientSessionId?: string | null` (le champ
   est identique des deux côtés), `metricSeries?: MetricSeries[]` et les types
   de séries. Ne pas rendre `clientSessionId` obligatoire : les scènes et les
   anciens appels `startActivity(sport, sessionId)` n’en ont pas.
2. **`activity/useGpsTracker.ts`** : garder la signature `restored` de A01 et
   son effet de rejeu, mais prendre la version qui appelle
   `rebuildMetricSeriesFromFixes`, publie `metricSeries` et renseigne
   `previousMetricFixRef`. Le tracker doit toujours être créé avec
   `autoPauseConfigForSport(...)` **avant** `addFix`.
3. **`ExplorerV2.tsx`, séance active** : aucun changement supplémentaire.
   A01 passe déjà `restored={{ clientSessionId, fixes }}` au hook ; les séries
   sont republiées par l’effet de reprise. Ne pas réécrire `metricSeries` dans
   `recordFromActivity` ni dans `appendSessionPoint` : les points restent la
   source de vérité.
4. **`ExplorerV2.tsx`, dernier bilan** : `points` est déjà lu avant
   `activityFromRecord`. Reconstruire les séries depuis ces points et les
   joindre au bilan :

   ```ts
   const summary = activityFromRecord(latest, route);
   if (!summary) return;
   const rebuilt = rebuildMetricSeriesFromPoints(
     points,
     latest.sport,
     useExplorerStore.getState().autoPauseEnabled ?? false,
   );
   useExplorerStore.setState({
     summary: { ...summary, metricSeries: rebuilt.series },
     summarySaved: latest.summarySaved ?? 'pending',
     sheet: 'summary',
     detent: 'full',
     camera: { type: 'overview' },
   });
   ```

   Alternative moins invasive : ajouter à `activityFromRecord` un troisième
   paramètre optionnel `metricSeries` et le poser dans l’objet retourné.
5. **Fin de séance** : `saveFinishedSession` n’a pas besoin des séries. Les
   points restent dans `session_points` et suffisent à reconstruire le bilan
   dans la fenêtre de reprise de 24 h. `forgetFinishedSession` les supprime au
   départ suivant : au-delà, une fiche historique A02 devra lire les points
   serveur ou un instantané de séries ; ce n’est pas fait ici.
6. **Capteurs et imports** : aucune source n’existe, donc aucune série cardio,
   cadence, puissance, température, calories ou pas n’est persistée. Le jour où
   une source réelle arrivera, ajouter un champ **optionnel** `metricSeries` à
   `LocalSessionRecord` (version 1, lecture défensive, absence acceptée) ou
   coordonner un magasin dédié avec A01. Ne jamais écrire ces valeurs dans
   `activity_points`, qui ne porte que la géométrie, et ne jamais les déduire
   de la distance ou du poids.
7. **Conflits de fusion** : `activity/useGpsTracker.ts`,
   `state/{types,store}.ts`, `sheet/SheetContent.tsx`,
   `ExplorerV2.tsx` et `docs/explorer-v2/MISSION_LOG.md`. La fusion doit
   conserver le rejeu A01 **et** les séries A04 ; elle ne doit remplacer ni le
   tracker ni le store.

### Limites honnêtes

- Le rejeu utilise le réglage de pause **courant**. Un changement entre la
  séance et le rechargement peut modifier la borne de reprise ; les valeurs
  déjà mesurées ne sont pas réécrites.
- `receivedAt` (horloge monotone de réception) n’est pas persisté par A01. Une
  correction de saut d’horloge appliquée en direct peut donc ne pas être
  reproduite à l’identique ; les points et agrégats A01 gardent leur propre
  limite documentée.
- Les séries de capteurs ne sont ni conservées ni restaurées : aucune source
  n’existe. L’interface continue de les afficher comme absentes.
- Après `forgetFinishedSession`, les points du bilan ne sont plus disponibles ;
  l’historique long terme reste dépendant de A02.
- La reprise part de la fiche locale A01 : une séance ouverte sur un autre
  appareil n’est pas découverte et ses séries ne sont pas fusionnées.

## Ce qui n’est pas fait, et pourquoi

1. **Import FIT/TCX** : aucun lecteur de fichier ni parseur n’est branché dans
   l’activité. Les champs `MetricInput` sont prêts, mais aucun code ne les
   remplit.
2. **HealthKit / Health Connect** : aucune permission, aucun plugin natif et
   aucun connecteur santé n’existe dans cette tranche.
3. **BLE** : aucune ceinture cardio, aucun capteur de cadence, de puissance ou
   de température n’est appairé.
4. **Calories** : aucun algorithme ni aucune source d’énergie. LKDV ne déduit
   pas de calories de la durée, de la distance, du poids ou du sport.
5. **Pas** : aucun podomètre. LKDV ne convertit pas une distance en nombre de
   pas.
6. **Persistance serveur** : `activity_sessions` ne porte que les agrégats
   (`distance_m`, `elev_gain_m`, `moving_s`) et `activity_points` ne porte que
   `lat`, `lng`, `ele`, `acc`, `speed`. Aucune migration n’a été écrite. Un
   rechargement perd les séries sur 8321e66 ; sur 4e0a25c, elles sont
   reconstruites depuis les points locaux (voir « Conservation et
   restauration »). Aucune série de santé n’est stockée côté serveur.
7. **Historique** : aucune fiche d’activité historique ne lit de séries. La
   surface livrée est le détail en direct et le bilan ; l’historique A02 reste
   à raccorder quand il exposera les points/séries. La reprise locale du bilan
   est bornée à la fenêtre A01 de 24 h et à la conservation des points.
8. **Preuve** : conformément à la consigne, aucun test, suite, build, lint ni
   `tsc` n’a été lancé. Les contrôles sont reportés à la fin de la mission.

## Dépendances aux connecteurs

Le contrat d’entrée est `MetricInput` :

```ts
{
  t: number;                    // instant de mesure, échelle tracker si possible
  elevationM?: number | null;   // m
  speedMs?: number | null;      // m/s
  heartRateBpm?: number | null; // bpm
  cadenceSpm?: number | null;   // pas/min ou tours/min selon le sport
  strokeRateSpm?: number | null;// coups/min
  powerW?: number | null;       // W
  temperatureC?: number | null; // °C
  caloriesKcal?: number | null; // total cumulé déjà estimé par la source
  steps?: number | null;        // total cumulé du podomètre
  source?: MetricSource;
  quality?: MetricQuality;
}
```

Règles pour un futur connecteur :

- fournir une valeur seulement quand elle existe ; `null`/absent est une
  lacune, pas un zéro ;
- déclarer la source (`sensor`, `import`) et la qualité (`measured`,
  `estimated`) ; une calorie importée reste `estimated` sauf preuve contraire ;
- ne jamais fournir une série cardio ou de pas synthétique pour « compléter »
  une séance ;
- ne pas mélanger deux sources dans une même série sans que le moteur ne la
  marque `mixed` ;
- ne pas écrire ces valeurs dans `activity_points` : ce magasin ne porte que
  la géométrie ;
- pour une série de capteur, prévoir un stockage additif coordonné avec A01
  (champ optionnel de `LocalSessionRecord` ou magasin dédié), avec lecture
  défensive et stratégie de reprise ; ne pas créer de migration Supabase pour
  des données de santé tant que la source et la base légale ne sont pas
  tranchées.
