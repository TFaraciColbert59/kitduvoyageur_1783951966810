## 2. Ce que les données réelles permettent

La licence est compatible ; la donnée, elle, n’est pas dans le périmètre
importé de l’Explorer. C’est ce second point qui bloque l’activation.

| Donnée / service | État vérifié dans le dépôt | Conséquence |
|---|---|---|
| `geo_pois` | **112 400 lignes** au dernier audit versionné (`AUDIT_VERIFIE.md`, 2026-10-28), réparties entre eau, sources, abris, campings, refuges et cabanes ; + 522 repères Alpine (sommets, belvédères, cols, parkings, arrêts) | Aucune ligne « vélo », « réparation » ou « recharge ». |
| Contrainte `geo_pois_subtype_check` | 13 valeurs autorisées (`20261101_explorer_v2_data.sql`) : `alpine_hut`, `wilderness_hut`, `shelter`, `camp_site`, `drinking_water`, `spring`, `peak`, `viewpoint`, `saddle`, `parking`, `trailhead`, `bus_stop`, `train_station` | Un sous-type vélo ne peut pas être inséré aujourd’hui : la base le refuserait. |
| Import `scripts/geo/import_geo_pois.ts` | `buildGeoPoisQuery` ne demande que les huttes, campings, points d’eau, abris et sources ; `parseGeoPois` ne connaît que ces natures | Même une exécution sur une zone vélo ne remonterait ni `shop=bicycle`, ni `amenity=bicycle_repair_station`, ni `amenity=charging_station`. |
| RPC `explorer_pois` | Mappe les sous-types connus ; tout autre sous-type tombe dans `else 'access'` | Une ligne vélo hypothétique serait affichée comme un « accès », pas comme un POI vélo. |
| Seed `supabase/seeds/explorer_v2_pois_alpes.sql` | `peak`, `bus_stop`, `saddle`, `viewpoint`, `parking` uniquement | Aucune preuve de donnée vélo dans le jeu versionné. |
| Source OpenStreetMap | Licence **ODbL 1.0**, attribution « © OpenStreetMap contributors » déjà présente dans le tiroir Calques | La licence **autorise** la réutilisation ; elle n’est pas le blocage. |
| Autre source (Overpass à la volée) | L’API `/api/explorer/osm/pois` existe pour l’ancien Explorer, mais l’Explorer v2 lit `explorer_pois` ; aucune requête réseau n’est ajoutée par cette tranche | On ne peut pas déclarer « disponible » un flux qui n’alimente pas la carte actuelle. |

Conclusion : les trois catégories ne remplissent pas la condition « la donnée
existe » dans LKDV. Leur licence OSM est, elle, déjà connue et compatible. Il
n’y a donc ni import, ni épingle, ni filtre actif inventés.

## 4. Pourquoi l’activation est refusée aujourd’hui

La fiche demande d’afficher « si la donnée existe, si elle concerne ce sport et
si elle est autorisée ». Les trois conditions ne sont pas réunies :

1. **Donnée** : aucune ligne vélo / réparation / recharge dans `geo_pois` ; la
   contrainte de sous-types l’interdit et l’import ne les demande pas.
2. **Sport** : `PoiKind` et `layerVisibility` ne portent pas ces familles ;
   aucun filtre ne peut les isoler, et le RPC les confondrait avec `access`.
3. **Autorisation** : la licence OSM ODbL est compatible, mais l’attribution et
   la source ne suffisent pas à rendre disponible une donnée absente.

Activer une ligne ou dessiner des épingles à partir de tags OSM non importés
serait une disponibilité inventée. La ligne désactivée est la seule réponse
conforme à la règle « zéro donnée inventée ».

## 8. Limites assumées

1. **Aucune donnée, aucun détail.** Les lignes sont informatives ; le toucher
   n’ouvre pas de fiche puisqu’aucun POI n’existe.
2. **Pas de compteur réel.** Afficher « 0 repère » serait exact mais laisserait
   croire à une couche vide plutôt qu’à une catégorie non branchée ; le texte
   dit « aucune ... importée ».
3. **Source et date.** OSM ODbL est la source prévue ; le schéma actuel ne
   porte pas de date de levé par POI, elle ne sera pas inventée.
4. **Recharge générique.** Une borne `amenity=charging_station` peut être
   automobile ; l’activation devra exiger `bicycle=yes` pour ne pas promettre
   une recharge vélo qui n’existe pas.
5. **Tests reportés.** Aucun `tsc`, lint, build, test unitaire, E2E ou capture
   n’a été exécuté dans cette tranche, conformément à la mission.
