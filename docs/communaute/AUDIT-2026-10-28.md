# Audit Communauté — drawers Créer et Explorer (28 octobre 2026)

Base auditée : `52b7e4b` (identique à `origin/main`, branche `claude/admiring-meitner-0ndwfq`). Lecture seule, aucun code modifié.

Référence design : `/compte` et ses drawers (`DrawerShell`, `SlotShell`, capsule 48 px, sous-capsule 30 px, verre Liquid Glass). Voir le skill `lkdv-ios27-page-refonte`.

---

## 1. Constat d'ensemble

La page `/communaute` (`src/app/communaute/page.tsx`) est déjà allégée : un fil de posts (`useCommunityFeed`), une barre de stories, et **deux drawers** :

| Drawer | Fichier | Rôle |
|---|---|---|
| Créer | `features/community/create/CreateDrawer.tsx` | 6 types : Publication, Carnet, Sortie, Kit, Club, Story |
| Explorer | `features/community/sections/CommunitySectionsDrawer.tsx` (495 l.) | 5 volets : Recherche, Pour toi, Carnets, Clubs, Sorties |

**Écart central avec la référence Compte** : les deux drawers reposent sur `CommunityDrawer`, un **demi-tiroir modal 50 dvh** en portail (backdrop, `aria-modal`, `body overflow hidden`). La référence est `DrawerShell`, où **le drawer remplace le contenu de la carte** (poignée, capsule 48 px icônes seules, pistes horizontales, sous-capsule flottante 30 px). Les deux surfaces n'ont donc ni la même géométrie ni la même mécanique de navigation.

## 4. Audit architecture et cohérence design

- **Deux coquilles de drawer concurrentes** : `CommunityDrawer` (50 dvh) + `CommunityFormDrawer` (76 dvh, portail propre) **et** `DrawerShell` du Compte. `CommunityFormDrawer` embarque même un second mode (`EmbeddedFormContext`) pour désactiver son portail quand il est inclus dans `CreateDrawer`. C'est un signe de dérive : il faut **un seul mécanisme**.
- **Doublons de gestion du glissement** : le code de poignée (`onPointerDown/Move/Up`) est copié dans `CommunityDrawer` **et** `CommunityFormDrawer` (≈ 30 lignes ×2).
- `features/community/feed/CommunityCreateDrawer.tsx` n'est **importé nulle part** (grep) : code mort à supprimer, il double `CreateDrawer.tsx`.
- Les formulaires partagent des états `busy/error` dupliqués : un hook `useCreateForm` (validation `zod`, brouillon, soumission) éviterait ~150 lignes répétées. La règle projet impose la **validation `zod` de toute entrée** ; elle n'est pas appliquée ici (validations manuelles).
- Les formulaires écrivent directement dans Supabase **depuis le client** (`carnets`, `events`, `materiel_kits`, `community_posts`). La règle projet réserve la logique métier aux couches de service ; une RPC ou une action serveur donnerait la transactionnalité manquante (C11) et centraliserait la validation.
- Tests : `features/community/**/__tests__` ne contient que `MentionPicker` et `mention-utils`. **Aucun test** pour `CreateDrawer`, les 6 formulaires ni `CommunitySectionsDrawer`.
- `any` : `user: any` partout (props des drawers et formulaires).

## 5. Audit performance (objectif : niveau Instagram)

Mesures statiques (aucun navigateur lancé dans cette session). Les chiffres réels seront pris avec Lighthouse / DevTools MCP avant et après chaque lot.

| # | Constat | Impact | Action |
|---|---|---|---|
| P1 | **Aucune virtualisation du fil** : `CommunityFeed` rend tous les posts chargés (pagination « Charger plus », pas de scroll infini). Chaque post embarque un panneau, un menu, un `ReportSheet`. | DOM et mémoire croissants, INP dégradé | `@tanstack/react-virtual` (déjà dans `package.json`) + `IntersectionObserver` pour l'infini |
| P2 | `select('*')` sur `community_posts` à chaque page, plus 2 requêtes `post_likes` / `post_saves` séquentielles après les profils (cascade de 3 allers-retours). | LCP / TTFB du fil | Colonnes explicites ; une vue ou RPC `feed_page(cursor)` renvoyant posts + auteur + états ; pagination **par curseur** (`created_at, id`) et non par `range()` |
| P3 | Le fil est rendu **entièrement côté client** (`'use client'` + `useEffect` → fetch). Rien n'est préchargé côté serveur. | LCP tardif, écran de squelette | Premier lot rendu serveur (Server Component + streaming), hydratation ensuite ; ou `prefetch` TanStack Query |
| P4 | Images en `<img loading="lazy">` brutes : **pas de `srcset`/`sizes`**, pas de dimensions, pas de placeholder flou. Les médias sont servis depuis `carnet-media` en pleine résolution. | Octets, CLS | Transformations Supabase Storage (`?width=…&quality=…`) ou `next/image` avec `sizes`, `aspect-ratio` fixe (le carré 1:1 existe déjà), vignette BlurHash/ThumbHash stockée à l'envoi |
| P5 | Vidéo : `preload="metadata"` partout ; pas de lecture pilotée par visibilité (`IntersectionObserver` > 50 %), pas d'affiche (`poster`), pas de HLS. | Données mobiles, batterie | Lecture/pause à la visibilité, `poster` généré à l'upload, pas de `autoplay` hors écran |
| P6 | `CommunityFeedPost` anime la **hauteur** de l'article (`el.style.height`) à l'ouverture du panneau. L'animation de `height` déclenche un reflow à chaque image. | Jank sur mobile | Animer `transform`/`opacity` (règle projet), ou réserver la place dès le rendu (carré 1:1 → hauteur connue) |
| P7 | `backdrop-filter: blur(25px) saturate(1.8)` sur **chaque post** (verre Compte) : coûteux en repeinte dans une liste. | Scroll saccadé sur Android bas de gamme | Verre uniquement sur les surfaces fixes ; fond opaque/gradient léger sur les posts hors écran (`content-visibility: auto` + `contain-intrinsic-size`) |
| P8 | `src/styles/community-feed.css` fait **44,8 Ko** et est importé dans le **layout racine** (`src/app/layout.tsx:14`) : il est donc chargé et parsé sur **toutes** les pages, pas seulement `/communaute`. Les styles des drawers y sont mêlés à ceux du fil. | CSS bloquant partout | Scinder : critique (fil + header) / différé (drawers). Charger les drawers via `next/dynamic` |
| P9 | `CreateDrawer`, `CommunitySectionsDrawer`, 6 formulaires, `MentionPicker` sont importés **statiquement** dans `page.tsx`, donc dans le bundle initial alors qu'ils ne servent qu'au clic. | JS initial, TBT | `dynamic(() => import(…), { ssr: false })` + préchargement au `pointerenter`/`touchstart` du bouton « + » |
| P10 | `CommunityStoriesBar` (980 l.) et `StoriesViewer` (569 l.) montent dans le chemin critique ; les vignettes lancent des sondes vidéo (`probe.preload = 'metadata'`). | Réseau au chargement | Différer le viewer ; vignettes statiques ; sonde vidéo à la demande |
| P11 | Le `<style dangerouslySetInnerHTML>` de `DrawerShell` réinjecte **~8 Ko de CSS à chaque instance**. | Parsing CSS répété | Passer ce CSS en feuille globale (`liquid-capsules.css` existe déjà) |
| P12 | `useCommunityFeed` recrée `fetchPage` à chaque changement de `userId`, et `refresh()` **recharge toute la page 1** après chaque création. | Requêtes inutiles | Insertion optimiste du nouveau post en tête (TanStack Query `setQueryData`), invalidation silencieuse en arrière-plan |
| P13 | `@vercel/speed-insights` est installé : s'assurer qu'il remonte bien **INP/LCP par route** pour piloter l'objectif. | Mesure | Définir un budget : LCP < 2,0 s, INP < 150 ms, CLS < 0,05 sur `/communaute` (4G simulée) |

Techniques Instagram pertinentes pour LKDV (sources Exa ci-dessous) : virtualisation à hauteur mesurée avec overscan ; images servies en 6 tailles avec `srcset` + `sizes` ; placeholders flous ; lecture vidéo pilotée par `IntersectionObserver` ; mises à jour optimistes (`useOptimistic`) ; pagination par curseur ; préchargement de la page suivante quand le sentinelle approche.
