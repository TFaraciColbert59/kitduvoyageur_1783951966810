# A03 / K6.02 / S2.05 — persistance et restitution des tours source FIT/TCX

Statut : implémentation locale, **aucun test, aucune suite, aucun build, aucun
lint, aucun `tsc`, aucun commit, aucune production** dans cette passe. Les
vérifications sont reportées à la fin du chantier, comme demandé.

Cette passe ferme le manque décrit par
[`A03-S2.05-tours.md`](A03-S2.05-tours.md) : les tours lus dans un fichier
FIT/TCX sont désormais **écrits avec la sortie**, **relus après rechargement**
et **rendus au propriétaire**. Le contrat reste strictement séparé des splits
calculés de l’Explorer.

## 1. Ce qui change réellement

| Couche | Avant | Après |
|---|---|---|
| Parseur | `NormalizedTraceLap` sans provenance de tour | champ `origin` explicite : `device` ou `synthetic` |
| Payload HTTP | aucun champ `laps` | `laps[]` borné, contrat `lapContract.ts` |
| RPC | `record_trace_import` (16 paramètres) | `record_trace_import_with_laps` (17e paramètre `p_laps`), l’ancienne reste intacte |
| Base | `trace_imports` seulement | `trace_import_laps`, RLS propriétaire, cascade |
| Détail serveur | `provenance` seulement | `provenance` + `laps` (`null` si indisponible, `[]` si aucun tour) |
| Drawer Sortie | mention « tours non restitués » | section « Tours du fichier », métriques réelles, badge source |
| RGPD | `trace_imports` | `trace_import_laps` ajoutée à l’export, au recomptage et à l’effacement |

## 2. Contrat de données

### 2.1 Côté client et route

`buildHikeSessionImportPayload` ajoute `laps: TraceImportLapPayload[]`. Chaque
tour porte uniquement les champs lus dans le fichier :

| Champ HTTP | Source | Règle |
|---|---|---|
| `index` | `NormalizedTraceLap.index` | entier 0..9 999, **égal à sa position** dans le tableau |
| `origin` | nouveau champ parseur | `device` ou `synthetic` uniquement |
| `startedAt` | `startedAt` | instant ISO avec fuseau, ou `null` ; jamais d’heure civile convertie |
| `elapsedSeconds` | `elapsedSeconds` | 0..31 536 000, ou `null` |
| `distanceM` | `distanceM` | 0..100 000 000, ou `null` |
| `averageSpeedMps` / `maxSpeedMps` | vitesse du tour | 0..1 000 m/s, ou `null` |
| `caloriesKcal` | calories du tour | 0..1 000 000, ou `null` |
| `averageHeartRateBpm` / `maxHeartRateBpm` | FC du tour | 0..300 bpm, ou `null` |
| `averageCadenceRpm` / `averageCadenceSpm` | cadence vélo / course | 0..500, ou `null` |
| `maxPowerW` | puissance max | 0..10 000 W, ou `null` |
| `intensity` / `triggerMethod` | chaînes du fichier | nettoyées, 1..64 caractères, ou `null` |
| `pointCount` | points rattachés | entier 0..100 000 |
| `trackCount` | nombre de segments | entier 0..100 000 |

`normalizeTraceImportLaps` (`src/features/hiking/import/lapContract.ts`) applique
ces bornes avant l’appel RPC et refuse :
- un tableau de plus de 10 000 tours ;
- un index non séquentiel ou hors bornes ;
- une origine autre que `device` / `synthetic` — donc tout split `computed` ou
  tour `manual` est rejeté ;
- un nombre non fini, un texte non textuel, un instant sans fuseau.

Un client antérieur qui n’envoie pas `laps` reste accepté : la sortie est écrite
sans tour, sans en inventer. Un corps non-import qui porterait `laps` est refusé.

### 2.2 Table `public.trace_import_laps`

Migration additive : `supabase/migrations/20261113110000_trace_import_laps.sql`.
Rollback : `supabase/migrations_down/20261113110000_trace_import_laps.down.sql`.

| Colonne | Type | Rôle |
|---|---|---|
| `id` | `uuid` | clé technique |
| `import_id` | `uuid not null` | provenance `trace_imports.id` |
| `session_id` | `uuid not null` | sortie `hike_sessions.id` |
| `owner_id` | `uuid not null` | propriétaire, `auth.uid()` à l’écriture |
| `lap_index` | `integer not null` | rang 0-based, unique par sortie |
| `lap_origin` | `text not null` | `device` ou `synthetic` |
| `started_at` | `timestamptz` | début UTC, ou `null` |
| `elapsed_seconds` | `double precision` | durée du tour |
| `distance_m` | `double precision` | distance du tour |
| `average_speed_mps` / `max_speed_mps` | `double precision` | vitesses |
| `calories_kcal` | `double precision` | calories |
| `average_heart_rate_bpm` / `max_heart_rate_bpm` | `double precision` | FC |
| `average_cadence_rpm` / `average_cadence_spm` | `double precision` | cadence |
| `max_power_w` | `double precision` | puissance max |
| `intensity` / `trigger_method` | `text` | chaînes source bornées |
| `point_count` / `track_count` | `integer not null default 0` | compteurs |

Contraintes structurantes :
- clé étrangère composite `(import_id, session_id, owner_id)` vers
  `trace_imports (id, session_id, owner_id)` : impossible d’attacher un tour à
  une autre sortie ou à un autre propriétaire, même par erreur applicative ;
- `unique (session_id, lap_index)` : un seul tour par rang dans une sortie ;
- `on delete cascade` : supprimer la provenance, la sortie ou le compte
  supprime les tours ;
- `check` sur toutes les bornes numériques, sur `lap_origin`, sur les longueurs
  de texte et sur `started_at` (1900–2100) ;
- index `(import_id, session_id, owner_id)` pour la cascade et la lecture par
  provenance, et index `(owner_id, session_id, lap_index)` pour la RLS,
  l’export RGPD et la lecture propriétaire.

Aucun point GPS, aucun tableau de segments et aucun contenu original n’est
dupliqué dans cette table : seuls les agrégats du tour sont conservés.

### 2.3 RPC `record_trace_import_with_laps(...)`

La RPC historique `record_trace_import` **n’est ni remplacée ni modifiée**. La
nouvelle fonction, `SECURITY DEFINER` avec `search_path = public, pg_temp` :

1. exige `auth.uid()` et valide la forme de `p_laps` (tableau, ≤ 10 000,
   objets, index entier, origine autorisée, compteurs entiers) ;
2. appelle `record_trace_import(...)` dans la même transaction : la sortie
   privée et la provenance sont créées exactement comme avant ;
3. si l’import existe déjà (`existing: true`), retourne `lap_count` sans
   réécrire ni compléter les tours ;
4. sinon, insère les tours avec le même `import_id`, `session_id` et
   `owner_id`, puis retourne `lap_count` ;
5. si une insertion de tour échoue, toute la transaction est annulée : jamais
   de sortie sans tours demandés, jamais de tours orphelins.

La route appelle cette RPC **uniquement si `laps.length > 0`**. Sans tour, elle
continue d’appeler l’ancienne RPC : un client ancien ou un import sans tour
fonctionne même avant la migration.

## 3. Découplage strict : tours source ≠ splits calculés

| Sujet | `trace_import_laps` (cette passe) | `ActivitySplit` Explorer (autre contrat) |
|---|---|---|
| Origine | fichier FIT/TCX | calcul depuis les points GPS ou geste manuel |
| Base temporelle | durée **du tour** (`elapsedSeconds`) | temps en mouvement (`movingS`) |
| Découpe | tours réels ou tour synthétique FIT | km, mile ou tour manuel |
| Identité | `lap_index` + `origin` | `kind` + `index` |
| Mesures | FC, puissance, cadence, calories | généralement absentes |
| Table | `trace_import_laps` | aucune table de splits dans cette passe |

Aucun code de cette passe n’importe `ActivitySplit`, ne fusionne les deux listes
et ne convertit un tour en split. La contrainte `lap_origin in ('device',
'synthetic')` et le validateur qui refuse `computed` / `manual` empêchent la
contamination inverse. Une future lecture des splits devra créer son propre
contrat, sa propre table et sa propre restitution ; elle ne pourra pas réutiliser
`trace_import_laps`.

## 4. Droits du propriétaire

- `trace_import_laps` a `ENABLE ROW LEVEL SECURITY`.
- Une seule policy : `SELECT` pour `authenticated` si
  `owner_id = (select auth.uid())`.
- Aucune policy `INSERT` / `UPDATE` / `DELETE` ; les grants d’écriture sont
  retirés à `public`, `anon` et `authenticated`. Seule la RPC écrit.
- La route filtre explicitement `owner_id = userId` **et**
  `session_id = outingId`.
- `loadOutingDetail` ne lit `provenance` et `laps` que si
  `session.user_id === userId`. Un participant, un lecteur de carnet ou un
  visiteur reçoit `provenance: null` et `laps: null`.
- Les tours ne contiennent ni coordonnée, ni nom de fichier, ni empreinte : le
  nom et l’empreinte restent dans `trace_imports`, également propriétaire seul.
- Suppression de la sortie ou du compte : cascade vers `trace_imports` puis
  `trace_import_laps`.

## 5. Restitution après rechargement

`GET /api/compte/sorties/[id]` renvoie désormais `laps` :

- `null` : table absente, lecture refusée/en erreur, ou lecteur non
  propriétaire. Le détail reste lisible et affiche « Tours indisponibles ».
- `[]` : table présente, aucun tour conservé (import antérieur à cette passe,
  ou fichier sans tour). Le détail affiche « Aucun tour conservé » et rappelle
  qu’aucun backfill n’est possible.
- `[...]` : tours dans l’ordre `lap_index`, rendus par `OutingLaps` dans le
  drawer Sortie.

La lecture est paginée par 1 000 lignes (plafond PostgREST par défaut) jusqu’à
10 000 tours. Le rendu détaille au plus 50 tours et indique combien d’autres
sont conservés : un fichier de 10 000 tours ne bloque pas le drawer.

Chaque tour affiche son rang, son origine (`Tour de l’appareil` ou `Déduit de
la séance`), le départ UTC, les métriques réellement présentes, le nombre de
points et de segments. Un FIT sans message `lap` est explicitement présenté
comme un tour reconstruit depuis la séance, jamais comme un tour déclenché sur
la montre. Les splits calculés ne sont ni affichés ni fusionnés dans cette
liste.

## 6. Compatibilité, déploiement et rollback

### 6.1 Ordre recommandé

1. appliquer les migrations sœurs selon leur ordre ;
2. appliquer `20261112123000_trace_import_dedupe.sql` (déjà requise) ;
3. appliquer `20261113110000_trace_import_laps.sql` ;
4. déployer le code de la route et du drawer.

### 6.2 Code déployé avant la migration

- Import **sans tour** : l’ancienne RPC est appelée, l’import fonctionne.
- Import **avec tour** : la nouvelle RPC manque (`PGRST202` / `42883`), la route
  répond `503` avec « La persistance des tours n’est pas encore disponible. »
  Elle ne perd **jamais** silencieusement les tours.
- Détail d’une sortie : `readImportLaps` retourne `null`, le détail reste
  lisible avec « Tours indisponibles ».

### 6.3 Migration appliquée avant le code

L’ancien code continue d’appeler `record_trace_import` : les imports existants
fonctionnent, sans tour. Après déploiement du code, les nouveaux imports
écrivent leurs tours. Les imports antérieurs restent sans tour ; un réimport du
même contenu retourne `existing: true` et **ne complète pas** rétroactivement
les tours (aucun backfill possible sans les données source historiques).

### 6.4 Rollback

Le down supprime la fonction versionnée, la table et la clé de portée ajoutée à
`trace_imports`. Il ne supprime ni les sorties ni les provenances. Le `DROP` de
`trace_import_laps` est irréversible pour les tours déjà écrits : exporter ou
archiver avant un rollback de production. Après rollback, les imports suivants
ne conservent plus de tour et `laps` vaut `null` ou `[]` selon l’état du code.

## 7. RGPD

- **Finalité** : restitution privée des tours d’une activité importée, au
  propriétaire seul. Aucun partage, aucune publication, aucune revente.
- **Minimisation** : une ligne par tour, agrégats seulement ; aucun point GPS,
  aucun contenu original, aucun nom de fichier dupliqué.
- **Données sensibles** : `average_heart_rate_bpm`, `max_heart_rate_bpm`,
  cadence et puissance sont des mesures physiologiques potentielles. Elles sont
  stockées uniquement parce que le fichier les contient, jamais dérivées ni
  complétées. L’AIPD doit évaluer cette finalité avant toute réutilisation
  santé ; voir `docs/compliance/03_AIPD_STRUCTURE.md`.
- **Droits** : `trace_import_laps` est ajoutée à `GDPR_USER_TABLES`
  (`owner_id`) et à `GDPR_OPTIONAL_TABLES` (table absente avant migration).
  L’export de portabilité inclut les tours ; la suppression du compte les
  efface par cascade et le recomptage A14 vérifie l’absence de résidu.
- **Sécurité** : RLS propriétaire, aucun accès anonyme, aucune écriture directe,
  `SECURITY DEFINER` à `search_path` verrouillé, propriétaire issu de
  `auth.uid()`.
- **Journalisation** : la route journalise le nombre de tours, jamais leur
  contenu, jamais la FC, jamais le nom de fichier ni l’empreinte.

## 10. Vérifications manuelles reportées

1. FIT avec plusieurs `lap` : enregistrer, recharger `/compte`, rouvrir la
   sortie ; le nombre de tours, l’ordre et les métriques réelles doivent
   correspondre à l’aperçu.
2. TCX avec plusieurs `<Lap>` : même contrôle, y compris un tour sans point
   géolocalisé (il reste lisible par ses métriques).
3. FIT sans message `lap` : un seul tour, badge « Tour reconstruit »,
   aucune mention de tour déclenché sur la montre.
4. Rejouer le même fichier : `existing: true`, aucun second stockage de
   provenance, aucun tour supplémentaire ; le nombre de tours existants est
   retourné.
5. Ouvrir la sortie avec un autre compte participant : `provenance: null`,
   `laps: null`, aucune FC ni nom de fichier dans la réponse réseau.
6. Déployer le code sans la migration : import avec tours → `503` explicite ;
   détail → « Tours indisponibles », pas de `500`.
7. Supprimer la sortie : les lignes `trace_import_laps` disparaissent par
   cascade ; l’export RGPD ne contient plus aucun tour.
8. Fichier à 10 000 tours : l’aperçu reste borné à 50, la lecture serveur
   pagine, le détail affiche 50 tours et le reste conservé.
