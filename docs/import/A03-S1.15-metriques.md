# A03 / K6.02 / S1.15 — métriques et séries FIT/TCX persistées

Statut : implémentation locale, **aucun test, aucune suite, aucun build, aucun
lint et aucun `tsc`** dans cette passe ; commit de fin de passe autorisé par la
demande du 2026-11-13, aucune production. Aucune migration n’est appliquée. Les
vérifications sont reportées à la fin du chantier, comme demandé.

Cette passe ferme le dernier manque de données de l’import FIT/TCX : les
**métriques de séance** et les **séries de mesures par point** étaient lues par
les parseurs, affichées dans l’aperçu, puis perdues à l’enregistrement. Elles
sont désormais écrites avec la sortie, relues après rechargement et rendues au
**propriétaire seul**.

## 1. Ce qui était encore perdu

| Couche | Avant cette passe | Après |
|---|---|---|
| Résumé `session` FIT | `NormalizedTraceImport.summary` vivait seulement en mémoire ; seuls distance et durée alimentaient `hike_sessions`. | Une ligne `trace_import_summaries`, une par import. |
| FC, cadence, puissance, température par point | Lues dans `NormalizedTrackPoint`, jamais envoyées à l’API. | Une ligne `trace_import_samples` par point portant au moins une mesure. |
| Distance source par point | `NormalizedTrackPoint.distanceM` lue mais absente de `positions_timed`. | Conservée dans `trace_import_samples.distance_m`. |
| Puissance moyenne FIT | `session.avg_power` et `lap.avg_power` (champ 19) n’étaient pas normalisés. | Normalisés, puis écrits dans le résumé et dans `trace_import_laps.average_power_w`. |
| Tours | Déjà persistés par `20261113110000_trace_import_laps.sql`. | Inchangés, sauf la colonne additive `average_power_w`. |
| Trace GPS, provenance, empreinte | Déjà persistées. | Inchangées. |

Ne sont **pas** revendiqués comme conservés : le fichier original, les champs
FIT non interprétés, les extensions TCX hors `TPX`, les valeurs 64 bits au-delà
de 2^53, les points non horodatés comme série temporelle, et les mesures
calculées par l’Explorer (`ActivitySplit`).

## 2. Contrat des valeurs

### 2.1 Résumé de séance FIT

`TraceImportSummaryPayload` (`src/features/hiking/import/series.ts`) recopie le
message FIT `session` :

| Champ HTTP | Colonne | Unité | Absence |
|---|---|---|---|
| `origin` | `summary_origin` | `fit_session` | toujours présent |
| `startedAt` | `started_at` | instant UTC | `null` si absent |
| `elapsedSeconds` | `elapsed_seconds` | s | `null` |
| `distanceM` | `distance_m` | m | `null` |
| `averageSpeedMps` / `maxSpeedMps` | `average_speed_mps` / `max_speed_mps` | m/s | `null` |
| `caloriesKcal` | `calories_kcal` | kcal | `null` |
| `averageHeartRateBpm` / `maxHeartRateBpm` | `average_heart_rate_bpm` / `max_heart_rate_bpm` | bpm | `null` |
| `averageCadenceRpm` / `averageCadenceSpm` | `average_cadence_rpm` / `average_cadence_spm` | tr/min ou pas/min | `null` |
| `averagePowerW` / `maxPowerW` | `average_power_w` / `max_power_w` | W | `null` |
| `activityTimerSeconds` | `activity_timer_seconds` | s | `null` |

Un TCX n’a pas de résumé de session : `summary` reste `null`. Aucun résumé n’est
calculé à partir des tours ou des points. Un FIT sans message `session` reste
également sans résumé.

### 2.2 Mesures de point

`TraceImportSamplePayload` recopie uniquement les points qui portent au moins
une des mesures encore perdues : distance source, FC, cadence, puissance ou
température. L’altitude et la vitesse sont recopiées quand elles accompagnent
un tel point, pour que la série reste lisible seule.

| Champ HTTP | Colonne | Unité | Absence |
|---|---|---|---|
| `index` | `sample_index` | rang 0-based | toujours présent, séquentiel |
| `origin` | `sample_origin` | `device` | toujours présent |
| `recordedAt` | `recorded_at` | instant UTC | `null` si la source n’avait pas de fuseau |
| `lapIndex` | `lap_index` | rang du tour | `null` si `lapIndex = -1` (aucun tour connu) |
| `distanceM` | `distance_m` | m | `null` |
| `altitudeM` | `altitude_m` | m | `null` |
| `speedMps` | `speed_mps` | m/s | `null` |
| `heartRateBpm` | `heart_rate_bpm` | bpm | `null` |
| `cadenceRpm` | `cadence_rpm` | tr/min | `null` |
| `cadenceSpm` | `cadence_spm` | pas/min | `null` |
| `powerW` | `power_w` | W | `null` |
| `temperatureC` | `temperature_c` | °C | `null` |

Aucune coordonnée, aucun nom de fichier et aucune empreinte ne sont dupliqués
dans cette table.

### 2.3 Absence, zéro, origine et unités

- **Absence** : la valeur est `null` en base et `null` dans le DTO. Un point qui
  ne porte aucune mesure n’est pas stocké.
- **Zéro réel** : `0` est accepté par les validateurs et les contraintes SQL, et
  affiché comme `0`. Aucun code ne remplace `0` par `null` ni l’inverse.
- **Origine** : `fit_session` pour le résumé, `device` pour chaque point. Le
  contrat refuse toute autre valeur, donc aucun split calculé ou mesure dérivée
  ne peut entrer dans ces tables.
- **Unités** : portées par les noms de colonnes/champs (`_m`, `_mps`, `_bpm`,
  `_rpm`, `_spm`, `_w`, `_c`, `_kcal`, `_seconds`) et rappelées dans ce
  document. Aucune conversion n’est faite à l’écriture ; les conversions
  d’affichage (m/s → km/h, m → km) sont faites dans l’UI.

## 3. Migration et stockage

Migration additive : `supabase/migrations/20261113124000_trace_import_metrics.sql`.
Rollback : `supabase/migrations_down/20261113124000_trace_import_metrics.down.sql`.

Prérequis : `20261112123000_trace_import_dedupe.sql` (`trace_imports`,
`record_trace_import`) et `20261113110000_trace_import_laps.sql`
(`trace_import_laps`, `record_trace_import_with_laps`). Aucune migration d’une
autre branche n’est modifiée.

### 3.1 `public.trace_import_summaries`

- une ligne par import (`unique (import_id)`) ;
- FK composite `(import_id, session_id, owner_id)` vers `trace_imports`, avec
  `on delete cascade` : impossible d’attacher un résumé à une autre sortie ou à
  un autre propriétaire ;
- `summary_origin = 'fit_session'` uniquement ;
- contraintes de bornes sur chaque mesure (FC 0–300 bpm, cadence 0–500,
  puissance 0–10 000 W, vitesse 0–1 000 m/s, distance 0–100 000 000 m,
  calories 0–1 000 000 kcal, durées 0–31 536 000 s, dates 1900–2100) ;
- `num_nonnulls(...) > 0` : une ligne sans aucune mesure est refusée.

### 3.2 `public.trace_import_samples`

- une ligne par point mesuré, `unique (session_id, sample_index)` ;
- `sample_index` 0–9999, séquentiel dans le contrat d’écriture ;
- FK composite identique, `on delete cascade` ;
- `sample_origin = 'device'` uniquement ;
- `lap_index` `null` ou 0–9999 ;
- contraintes de bornes sur toutes les mesures ; `temperature_c` entre −100 et
  100 °C, `altitude_m` entre −1 000 et 10 000 m ;
- `num_nonnulls(...) > 0` : un point sans mesure n’est pas stocké ;
- index `(import_id, session_id, owner_id)` et
  `(owner_id, session_id, sample_index)`.

### 3.3 `trace_import_laps.average_power_w`

La migration ajoute une colonne nullable `average_power_w` et sa contrainte
0–10 000 W. Elle ne modifie **pas** la migration `20261113110000` : le champ FIT
`lap.avg_power` (champ 19) est normalisé côté parseur, envoyé dans
`laps[].averagePowerW`, puis complété par la nouvelle RPC dans la même
transaction.

## 4. Écriture atomique

RPC `public.record_trace_import_with_metrics(...)`, `SECURITY DEFINER`,
`search_path = public, pg_temp`, exécutable par `authenticated` uniquement.

1. propriétaire = `auth.uid()` ; aucun paramètre propriétaire, `session_id`,
   `import_id` ou `visibility` n’est accepté ;
2. validation de forme : `p_laps`, `p_summary` et `p_samples` sont des JSON de
   types attendus ; index entiers et séquentiels ; origines fermées ;
3. appel de `record_trace_import_with_laps(...)` dans la même transaction : la
   sortie privée, la provenance et les tours sont créés exactement comme avant ;
4. si l’import existe déjà (`existing: true`), retour des compteurs réels sans
   réécriture ni complément rétroactif ;
5. sinon, insertion du résumé, mise à jour de `average_power_w` des tours, puis
   insertion des mesures ;
6. toute erreur annule l’ensemble : jamais de sortie sans métriques demandées,
   jamais de métriques orphelines.

La route appelle cette RPC **uniquement** si un résumé ou des mesures sont
présents. Sans métrique, elle garde les RPC précédentes : un client ancien ou un
import sans capteur fonctionne avant la migration.

## 5. Bornes et volume

| Limite | Valeur | Où elle est appliquée |
|---|---|---|
| Mesures de point par import | 10 000 | `TRACE_IMPORT_MAX_PAYLOAD_SAMPLES`, route, RPC et `check` SQL |
| Index de mesure | 0–9 999 | validateur, RPC, `check` |
| Résumé | 1 ligne | `unique (import_id)` |
| Tours | 10 000 | contrat et table existants |
| Points lus par le parseur | 100 000 | `TRACE_IMPORT_LIMITS.maxPoints` |
| Fichier original | 16 Mio | parseur, route, `trace_imports` |
| Texte de tour | 64 caractères | contrat et table existants |

Ordre de grandeur : une mesure de point complète pèse environ 150–250 octets en
JSON (davantage si tous les champs nuls sont sérialisés). 10 000 mesures restent
donc de l’ordre de 1,5 à 2,5 Mo par import, avant les positions et les tours. Le
résumé ajoute une ligne négligeable. La projection est échantillonnée
uniformément, extrémités conservées : le fichier complet reste sur l’appareil,
et **aucun point supplémentaire n’est inventé** pour atteindre la borne.

## 6. Droits du propriétaire

- `trace_import_summaries` et `trace_import_samples` ont
  `ENABLE ROW LEVEL SECURITY`.
- Une seule policy par table : `SELECT` pour `authenticated` si
  `owner_id = (select auth.uid())`. Aucune policy `INSERT` / `UPDATE` /
  `DELETE` ; les grants d’écriture sont retirés à `public`, `anon` et
  `authenticated`. Seule la RPC écrit.
- `loadOutingDetail` ne lit le résumé et les mesures que si
  `session.user_id === userId`, puis filtre explicitement
  `owner_id = userId` **et** `session_id = outingId`.
- Un participant, un lecteur de carnet ou un visiteur reçoit
  `summary: null` et `samples: null` : aucune FC, cadence, puissance ni
  température ne sort du propriétaire.
- Les coordonnées ne sont pas dupliquées dans ces tables ; la trace reste dans
  `hike_sessions`, sous ses propres policies.
- Suppression de la sortie ou du compte : cascade vers `trace_imports`, puis
  vers `trace_import_laps`, `trace_import_summaries` et
  `trace_import_samples`.

## 7. Restitution après rechargement

`GET /api/compte/sorties/[id]` renvoie deux champs supplémentaires :

- `summary` : `null` si le registre est absent, si le lecteur n’est pas
  propriétaire, si l’import n’a pas de résumé (TCX, FIT sans `session`) ou si
  l’import est antérieur à cette passe ; sinon les valeurs réellement stockées,
  `null` par champ absent.
- `samples` : `null` si le registre est absent, si le lecteur n’est pas
  propriétaire ou si la provenance est illisible ; `[]` si la table est lisible
  mais ne contient aucune mesure ; sinon les mesures dans l’ordre
  `sample_index`.

Le drawer Sortie ajoute une section « Métriques de la montre » réservée au
propriétaire :

- tuiles du résumé : calories, FC moyenne/max, cadence moyenne, puissance
  moyenne/max, vitesses moyenne/max, temps minuteur ;
- une sparkline par série réellement présente (FC, cadence vélo/course,
  puissance, température, vitesse, altitude, distance source), avec le nombre
  de mesures et les valeurs du premier et du dernier point ;
- un état vide explicite : « aucune valeur conservée » ou « séries
  indisponibles », jamais une valeur inventée.

Le rendu est borné à 240 points par sparkline, sans interpolation : les valeurs
affichées restent celles du fichier.

## 8. RGPD

- **Finalité** : restitution privée des métriques d’une activité importée, au
  propriétaire seul. Aucun partage, aucune publication, aucune revente.
- **Minimisation** : le résumé ne contient que les totaux de session FIT ; les
  séries ne contiennent que les mesures présentes, sans coordonnées, sans nom
  de fichier et sans empreinte. Aucun contenu original n’est conservé.
- **Données sensibles** : FC, cadence et puissance sont des mesures
  physiologiques potentielles. Elles sont stockées uniquement parce que le
  fichier les contient, jamais dérivées ni complétées. L’AIPD doit évaluer cette
  finalité avant toute réutilisation santé ; voir
  `docs/compliance/03_AIPD_STRUCTURE.md`.
- **Droits** : `trace_import_summaries` et `trace_import_samples` sont ajoutées
  à `GDPR_USER_TABLES` (`owner_id`) et à `GDPR_OPTIONAL_TABLES` (tables absentes
  avant migration). L’export de portabilité les inclut ; la suppression du
  compte les efface par cascade et le recomptage A14 vérifie l’absence de
  résidu.
- **Sécurité** : RLS propriétaire, aucun accès anonyme, aucune écriture directe,
  `SECURITY DEFINER` à `search_path` verrouillé, propriétaire issu de
  `auth.uid()`.
- **Journalisation** : la route journalise le nombre de mesures et la présence
  d’un résumé, jamais leur contenu, jamais la FC, jamais le nom de fichier ni
  l’empreinte.

## 9. Compatibilité, déploiement et rollback

Ordre recommandé :

1. appliquer `20261112123000_trace_import_dedupe.sql` ;
2. appliquer `20261113110000_trace_import_laps.sql` ;
3. appliquer `20261113124000_trace_import_metrics.sql` ;
4. déployer le code de la route et du drawer.

- **Code avant la migration** : un import avec métriques répond `503` avec un
  message explicite ; il ne perd pas silencieusement les mesures. Le détail
  reste lisible : `summary` et `samples` valent `null`. Les tours existants
  restent lisibles grâce à la lecture `select('*')` de `trace_import_laps`, même
  si `average_power_w` n’existe pas encore.
- **Migration avant le code** : les anciens imports continuent de fonctionner
  sans métriques ; les nouveaux imports les écrivent après déploiement. Aucun
  backfill : les imports antérieurs n’ont jamais stocké ces valeurs.
- **Rollback** : le down supprime la RPC, les deux tables et la colonne
  `average_power_w`. Il ne supprime ni les sorties, ni les provenances, ni les
  tours. Le `DROP` des tables est irréversible pour les mesures déjà écrites :
  exporter ou archiver avant un rollback de production.

## 12. Vérifications manuelles reportées

1. FIT avec `session` et plusieurs `lap` : enregistrer, recharger `/compte`,
   rouvrir la sortie ; le résumé (calories, FC, cadence, puissance, vitesses,
   minuteur) et les séries doivent correspondre à l’aperçu.
2. TCX avec FC, cadence, puissance et température par point : les séries
   apparaissent ; le résumé reste absent (le TCX n’en porte pas).
3. FIT sans capteur : aucune série n’est inventée ; la section affiche son état
   vide.
4. Un point à `0` (par exemple puissance ou température) doit s’afficher `0`,
   pas « absent ».
5. Un point sans horodatage UTC ne doit pas produire d’instant inventé ; la
   série reste ordonnée par `sample_index`, `recordedAt` vaut `null`.
6. Ouvrir la sortie avec un autre compte participant : `summary: null`,
   `samples: null`, aucune FC ni nom de fichier dans la réponse réseau.
7. Déployer le code sans la migration : import avec métriques → `503`
   explicite ; détail → `summary`/`samples` à `null`, pas de `500` ; les tours
   existants restent lisibles.
8. Rejouer le même fichier : `existing: true`, aucun second stockage de
   résumé/mesure, compteurs réels retournés.
9. Supprimer la sortie : les lignes `trace_import_summaries` et
   `trace_import_samples` disparaissent par cascade ; l’export RGPD ne contient
   plus aucune mesure.
10. Fichier à plus de 10 000 points mesurés : la projection est bornée à
    10 000, les extrémités sont conservées et l’aperçu indique le nombre réel de
    mesures lues.
