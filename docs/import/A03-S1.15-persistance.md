# A03 / K6.02 / S1.15 — persistance et déduplication des imports de trace

Statut : conception et implémentation locales, **aucune migration appliquée, aucun
test, aucune suite, aucun build, aucun commit, aucune production** dans cette passe.
Les vérifications sont reportées en fin de chantier, comme demandé.

## 1. Problème fermé

La route historique `POST /api/hike-sessions` dédupliquait un import sur
`(user_id, started_at)`. Deux fichiers **différents** démarrant à la même seconde
étaient donc confondus : le second import recevait l'identifiant du premier et son
contenu était perdu. À l'inverse, deux imports **identiques** n'étaient reconnus
que si leur heure de départ coïncidait.

La déduplication est désormais fondée sur le couple **propriétaire + empreinte
SHA-256 du contenu original**. L'heure de départ n'entre plus dans la clé d'un
import. Deux contenus différents créent deux sorties, même s'ils commencent à la
même seconde ; un rejeu du même contenu retourne la sortie existante.

## 2. Contrat client → API

`buildHikeSessionImportPayload` ajoute au corps existant :

| Champ | Type | Règle |
|---|---|---|
| `source` | `'fit' \| 'tcx'` | Format réellement détecté par le parseur, jamais déduit du seul nom de fichier. |
| `sourceFingerprint` | `string` | `sha256:` + 64 hexadécimaux minuscules, calculé sur les octets originaux. |
| `sourceFileName` | `string \| null` | Nom réel du fichier, réduit à son dernier segment et borné à 255 caractères. |
| `sourceByteLength` | `number` | Taille originale, `1..16 Mio` (`TRACE_IMPORT_LIMITS.maxBytes`). |

La route conserve son contrat de réponse `{ sessionId, carnetId, existing }`.
`existing: true` signifie désormais **même empreinte pour ce propriétaire**, et non
plus « même heure de départ ».

Les bornes `startedAt` et `endedAt` doivent être des instants ISO 8601 avec fuseau
(`Z` ou offset). Une heure civile nue est refusée : l'import ne peut pas convertir
sans invention ce que le parseur n'a pas qualifié en UTC.

Le contrat historique reste intact : un appel sans `source` ni `sourceFingerprint`
suit exactement le chemin GPS antérieur (contrôle `(user_id, started_at)`, carnet
automatique, moments). `HikeSessionService`, `OfflineManager` et les autres
appelants n'ont rien à changer.

Le décodage et la validation du contrat sont isolés dans
`src/features/hiking/import/importContract.ts` (module pur, sans Next ni
Supabase) : `resolveTraceImportIdentity`, `validateTraceImportPayload` et
`boundedImportFileName`. La route les appelle, la RPC revalide les mêmes bornes.

## 3. Modèle de persistance

Migration additive : `supabase/migrations/20261112123000_trace_import_dedupe.sql`.
Rollback : `supabase/migrations_down/20261112123000_trace_import_dedupe.down.sql`.

Nouvelle table `public.trace_imports` :

| Colonne | Rôle |
|---|---|
| `id uuid` | Clé technique. |
| `owner_id uuid not null` | `auth.uid()` au moment de l'import ; FK `auth.users(id) ON DELETE CASCADE`. |
| `session_id uuid not null unique` | Sortie dérivée `hike_sessions.id` ; FK `ON DELETE CASCADE`. |
| `source text not null` | `fit`, `tcx` ou `gpx`. |
| `source_fingerprint text not null` | `sha256:` + 64 hexadécimaux. |
| `source_file_name text` | Nom d'origine borné, `NULL` accepté. |
| `source_byte_length integer` | `1..16 777 216`, `NULL` accepté. |
| `correlation_id uuid` | Corrélation technique, `NULL` accepté. |
| `imported_at timestamptz not null default now()` | Date du premier import de cette empreinte. |

Contraintes d'unicité :

- `unique (owner_id, source_fingerprint)` : **la** clé de déduplication ;
- `unique (session_id)` : une sortie ne peut être reliée qu'à une seule provenance.

Le format source n'est **pas** dans la clé. C'est volontaire : l'empreinte porte sur
le contenu, donc sur les octets qui déterminent le format. Ajouter `source` à la clé
permettrait à un client de contourner la déduplication en annonçant un autre format
pour le même contenu. La provenance `source` est conservée à titre informatif.

Aucune colonne de `hike_sessions` n'est ajoutée ou modifiée. La provenance reste
donc hors de la table dont les policies de partage de carnet peuvent exposer les
lignes brutes, et les branches Explorer/Carnet qui modifient `hike_sessions` ne
créent aucun conflit de schéma avec cette migration.

## 4. Écriture atomique

RPC `public.record_trace_import(...)`, `SECURITY DEFINER`, `search_path = public,
pg_temp`, exécutable par `authenticated` uniquement.

Déroulé, dans une seule transaction :

1. propriétaire = `auth.uid()` ; aucun paramètre propriétaire n'est accepté ;
2. validation stricte du format, de l'empreinte, des bornes temporelles, de la
   distance, de la durée, du dénivelé, de l'altitude, de la taille source et des
   volumes JSON ;
3. verrou transactionnel `pg_advisory_xact_lock(hashtextextended(owner:fingerprint))`
   pour sérialiser deux onglets ou deux requêtes concurrentes sur le même contenu ;
4. lecture de `trace_imports` : si la ligne existe, retour de `session_id` sans
   aucune réécriture ;
5. sinon, insertion de la sortie `hike_sessions` avec `carnet_id = NULL`,
   `visibility = 'private'`, `trip_id` absent, puis insertion de la provenance ;
6. retour `{ session_id, carnet_id, existing }`.

Si l'une des deux insertions échoue, la transaction entière est annulée : jamais de
sortie sans provenance, jamais de provenance sans sortie. L'index unique reste le
garde-fou final si un appelant contournait le verrou.

La RPC ne crée **aucun** carnet, **aucun** moment et **aucun** lien de voyage. Un
import ne peut pas devenir public par ce chemin.

## 5. Limites de données et de fichiers

| Limite | Valeur | Où elle est appliquée |
|---|---|---|
| Fichier original | 16 Mio | Parseur (`TRACE_IMPORT_LIMITS.maxBytes`), route (`sourceByteLength`), RPC. |
| Points lus | 100 000 | Parseur (`maxPoints`). |
| Tours | 10 000 | Parseur (`maxLaps`). |
| Messages FIT | 250 000 | Décodeur FIT (`maxMessages`). |
| Points projetés vers l'API | 15 000 | `TRACE_IMPORT_MAX_PAYLOAD_POINTS`, route, RPC (`positions_geojson` et `positions_timed`). |
| Points d'intérêt | 1 000 | RPC `p_poi_events` ; un import envoie `[]`. |
| Titre | 120 caractères | Route et RPC. |
| Notes | 2 000 caractères | Route et RPC. |
| Nom de fichier | 255 caractères | Route et RPC. |
| Empreinte | 71 caractères | Route et contrainte SQL. |

Le fichier original n'est jamais téléversé. La limite de 16 Mio porte sur le
fichier local ; la requête réseau ne porte que la projection échantillonnée à
15 000 points, ce qui reste sous les limites de charge de la plateforme.

## 6. Sécurité et confidentialité

### Modèle de menace

| Risque | Contrôle |
|---|---|
| Déduplication entre comptes | Clé `(owner_id, source_fingerprint)` ; la RPC ne lit et n'écrit que pour `auth.uid()`. |
| Course entre deux onglets | Verrou transactionnel + index unique + transaction unique. |
| Écriture partielle | Une seule fonction ; les deux insertions réussissent ou échouent ensemble. |
| Écriture directe malveillante | `trace_imports` : `ENABLE ROW LEVEL SECURITY`, policy SELECT propriétaire seulement, aucun `INSERT/UPDATE/DELETE` pour `authenticated`, `anon` sans grant. Seule la RPC écrit. |
| Fuite de provenance via un carnet | Provenance dans une table séparée, propriétaire seul ; un import crée `carnet_id = NULL`. |
| Fuite du fichier original | Aucun octet original n'est stocké ; seuls l'empreinte, le nom et la taille le sont. |
| Injection / balisage | RPC paramétrée, aucun SQL dynamique ; titre, notes et nom de fichier nettoyés (`<`, `>`, caractères de contrôle) et bornés. |
| Épuisement de ressources | Bornes §5 ; la route refuse avant l'appel, la RPC revalide. |
| Élévation de privilèges | `SECURITY DEFINER` avec `search_path` verrouillé, `EXECUTE` retiré à `PUBLIC`, aucun paramètre `owner_id`, `carnet_id`, `trip_id` ou `visibility`. |
| Journalisation de données personnelles | Les logs serveur ne contiennent ni empreinte ni nom de fichier ; seulement `source` et le booléen `import_existing`. |

### Limite assumée : l'empreinte est déclarée par le client

Le fichier original reste sur l'appareil (exigence de confidentialité du parcours).
Le serveur ne peut donc pas recalculer l'empreinte des octets originaux. Un
utilisateur authentifié peut déclarer une empreinte arbitraire **pour son propre
compte** :

- il ne peut pas lire ni écraser la provenance d'un autre compte (clé et RLS
  propriétaires) ;
- il peut, au pire, se bloquer lui-même en associant une fausse empreinte à une
  sortie : une réimportation du vrai fichier retournera cette sortie existante ;
- le format, la longueur et le préfixe sont validés, ce qui empêche les valeurs
  libres et les collisions accidentelles de format.

Une vérification serveur exigerait de téléverser le fichier original ou de faire
signer l'empreinte par un composant de confiance. Ce choix est hors périmètre et
contredirait la promesse « l'original ne quitte pas l'appareil ».

### RGPD

- `trace_imports` est ajouté au registre `GDPR_USER_TABLES` avec `owner_id`, donc
  inclus dans l'export de portabilité et le recomptage de suppression.
- La table est déclarée optionnelle dans `GDPR_OPTIONAL_TABLES` : si le code est
  déployé avant la migration locale, l'export et la suppression ne échouent pas ;
  une fois la table présente, elle est comptée normalement.
- La suppression de la sortie ou du compte supprime la provenance par cascade.
- Le nom de fichier peut contenir des données personnelles : il est propriétaire
  seul, nettoyé, borné, jamais journalisé et jamais exposé dans une réponse
  publique.
- L'empreinte est un identifiant pseudonyme, pas un secret ; elle n'est lisible que
  par le propriétaire via RLS.

## 8. Déploiement et rollback

Ordre de déploiement recommandé :

1. appliquer les migrations sœurs selon leur ordre chronologique ;
2. appliquer `20261112123000_trace_import_dedupe.sql` ;
3. déployer le code de la route et du drawer.

Si le code est déployé avant la migration, un import répond `503` avec un message
explicite ; il ne revient **pas** silencieusement au contrôle `started_at`. Si la
migration est appliquée avant le code, aucun import n'écrit encore dans
`trace_imports` ; les imports suivants après déploiement du code seront dédupliqués
par empreinte. Aucun backfill n'est possible pour les imports antérieurs : leurs
empreintes n'ont jamais été conservées et les originaux sont restés sur les
appareils.

Rollback `20261112123000_trace_import_dedupe.down.sql` :

- supprime la RPC et `trace_imports` ;
- **ne supprime pas** les lignes `hike_sessions` déjà créées : ce sont des données
  utilisateur privées, pas des artefacts de migration ;
- les imports suivants reviennent au contrôle historique `(user_id, started_at)`.

## 9. Hors périmètre de cette passe

- Stockage privé des fichiers originaux : non ouvert, non nécessaire à la
  déduplication.
- Export dédié des imports et reprise : la provenance est persistée, mais l'écran
  Sorties ne l'affiche pas encore après rechargement.
- Backfill des imports antérieurs : impossible sans les originaux et sans
  empreintes historiques.
- Vérification serveur de l'empreinte : voir §6.
- Tests, suites, build, migration réelle, production, commit : reportés.
